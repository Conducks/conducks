# todo24 — the fallback register: no degraded answer looks like a confident one
Status: done
- Acceptance: every fallback in the register either refuses or labels its guess, and nothing a pulse computes is left in memory.

## Context

A nine-lane trace of the whole system catalogued every fallback and labelled each REFUSES or GUESSES.
The register is in `docs/visuals/system-trace.html`, with a `file:line` anchor per row; every row was
re-opened and read by hand after the lanes reported it, and one claim did not survive that check.

The count is 22 fallbacks, 14 of them guessing. A guess is not the problem — a structural tool that
stops whenever it is unsure returns an empty graph. The problem is a guess that is indistinguishable
from a fact once written, because then every downstream consumer treats it as one.

Three decisions landed with the first pass: ADR 0044 (a check that ran on nothing is not a pass),
0045 (an edge moves through the index), 0046 (confidence prices the guess). What remains is the other
guessers, and one inconsistency 0046 introduced on its way in.

Order matters. Phase 2 is the largest and Phase 1 is a question that changes what Phase 2 should do
about drift, so Phase 1 goes first even though it is small.

## Phase 0 — honest verdicts, landed with ADR 0044
- Builds: 0044
- [x] `drift` reported STABLE from a comparison that never ran — a thrown query, or two pulses with nothing in common, both left `deltas` empty and `deltas.some(...)` is false on an empty array. Verified by `npm test -- unearned-pass`, and by running `conducks drift` on this vault: was "✅ stable across 0 symbols", now "⚠️ no symbols were comparable"
- [x] `guard` turned that into "✅ Stability acceptable: Global risk (0.000)" — a pre-commit gate passing a check it never made. Now reports NOT ASSESSED and still exits zero, because a first pulse legitimately has no baseline. The CLI's own `✅` prefix reproduced the bug one layer up and is gone too; verified by running `conducks guard`
- [x] `persistence.save()` accepted a `metadataOnly` flag it never read, while two call-site comments described it as the switch suppressing row writes — so the obvious fix for a binder whose output vanished was to flip it, which would have changed nothing. Parameter and both comments removed; `grep -rn metadataOnly src/` returns only the note explaining its absence

## Phase 6 — the governance gate reports only real violations
- Builds: 0044

First, `matchLabel: STRUCTURE` was the only selector available and STRUCTURE covers 55 interfaces and type aliases as well as 42 classes, so every data shape was asked to implement a component contract — 83 of the 97. A `matchSemanticKind` selector now narrows within a canonical kind
- [x] Second, `endsWith('::' + target)` compared case-sensitively against ids that are case-folded on insert, and an unresolved heritage target carries no `::` prefix at all — it is the bare name. The message printed `found [conduckscomponent]` beside `Expected [ConducksComponent]` on every one of them, and nobody read it, because it was one line in ninety-seven. Heritage now matches on the SYMBOL, case-insensitively
- [x] Third, and found by making the first fix wrongly: a rule matching zero nodes reported clean. The first attempt used the vault's column name `semantic_kind` where the in-memory field is `kind`, which silently turned the whole rule off and looked like success — the same failure the `matchLabel` guard above it was written to prevent, in a new variant. A zero-match now fails the report for ANY rule rather than for an invalid label only
- [x] Measured against the graph, not asserted: 42 classes under `src/lib/domain/`, 28 implementing `ConducksComponent`, 14 not. `audit` now reports exactly those 14. Enforced by `tests/unit/domain/governance/sentinel-scope.test.ts`, three of whose four cases were confirmed red against the original defects
- [-] CARRIED to todo25#P7 and closed there, which carries the three design questions together — they are one conversation about identity, not three tickets. The 14 are a real finding nobody has judged yet: `DriftEngine`, `AuditService`, `QueryService`, `MicroPulseService`, `WorkerPool` and nine others are domain services that do not implement the contract the other 28 do. Decide whether the rule is right and the classes should conform, or the rule is too broad and should name what it actually requires. UNMEASURED whether implementing it would change any behaviour

## Phase 5 — the edges point at things that exist
- Builds: 0046
- [x] `node:` builtins were never induced: the namespace of `node:fs::readdirsync` is `node:fs`, and `externalPrefixes` is an exact-match list, so 214 edges into node builtins stayed dangling while every other external reference was absorbed. Any `node:`-prefixed namespace now counts as external — measured 214 to 0
- [x] Alias specifiers were never resolved. `registerLocalBinding` stored the RAW specifier, so `CallProcessor` built ids like `@/registry/index.js::registry.audit.advise` — 817 dangling edges, the largest single group, because an alias is not a path any node is keyed by. The binding now stores the resolved path, and `ImportProcessor` resolves `@/x` and `~/x` by matching the tail of a real project path rather than by reading tsconfig, so it needs no knowledge of the mapping. Ambiguity refuses, per 0046. Measured 817 to 23
- [x] A call whose receiver is a literal or an expression is no longer recorded as a reference. A regex literal (`/\/architecture\//.test`) and a chained call (`id.split('::').pop`) are not symbols and their edges could never resolve. Measured: regex 77 to 10, chains 92 to 7
- [x] The exact-match `externalPrefixes` list could never have worked, because a real specifier carries the PACKAGE as its namespace — `@jest/globals::jest.fn`, `minimatch::minimatch`, `child_process::execsync`. 360 of the 436 dangling edges on a clean vault were npm packages. The rule that actually separates local from external is whether the namespace looks like a PATH; anything else is a module this project does not contain. Measured 436 to 53 dangling
- [x] MEASURED, and it reframes what virtual induction was doing: of 3,093 call edges the guard removes, 2,953 DID resolve — every one of them to a `library_symbol` node that induction had itself created for that same expression fragment. Induction was not absorbing external references there, it was manufacturing nodes for junk and closing the loop. Every node id containing a paren in this vault is such a node (1,313 of them) bar a single route id. The dangling count alone could not have shown this, because the junk resolved
- [-] CARRIED to todo25#P7 and closed there. NOT FIXED, and the obvious fix is WRONG — which is the useful part. Nodes from old pulses are never swept: before the vault was rebuilt it held 6,589 nodes against 3,576 written by the latest pulse, 3,013 of them junk induced by a build that predated the literal-receiver guard. But `pulseId` cannot drive the sweep, because it does not mean "last seen". A rebuilt vault, two pulses in, already carries two ids: 3,624 nodes re-stamped by the wave flush and 1,653 induced nodes still carrying the pulse that FIRST created them — induction skips a node the reloaded graph already holds, so it never re-stamps them. Deleting rows whose pulseId is not the newest would therefore delete every still-valid external symbol. Fixed when a pulse can distinguish "not seen this run" from "not re-written this run"; decide it in an ADR, since the answer changes what pulseId means
- [-] CARRIED to todo25#P7 and closed there. `PULSES_TO` still dangles on both ends — 41 targets and its sources are variable names rather than node ids. Same design question as todo24#P4, and the same ADR should settle both

## Phase 4 — virtual induction reaches the vault
- Builds: 0042
- [x] `induceVirtualLibraries` logged "Resonated with 2,691 virtual ecosystem symbols" and persisted none, because it runs after the last wave flush and the pulse's final `save()` writes no node rows. Same failure and same remedy as cross-service binding (todo22#P15): the induced nodes are collected and written with an explicit `saveNodes` inside the pulse transaction
- [x] The cost it was leaving behind is measured, not asserted: 6,808 of 13,418 edges in this repo's vault — 51% — pointed at a target with no node, and the targets were `global::process`, `path.resolve`, `db.all`. On a fixture exercising all three reference kinds, dangling edges go 4 → 0 and virtual nodes 0 → 2
- [x] Enforced by `tests/integration/features/virtual-induction.test.ts`, which queries the vault directly. Its FIRST version asserted against `audit` and `query` output and passed against a build with the persist call removed — the CLI surfaces are not sensitive to whether the rows exist, which is the same blindness that let the bug live. Confirmed red against the unfixed build: 0 virtual nodes, 4 dangling
- [x] `bindPulseCircuits` had the identical shape AND a second, independent cause, either of which was enough alone. First, it never added its edges to `lastResonanceEdges`, so they were discarded with everything else built after the flush. Second, the TypeScript query captured assignments only from `assignment_expression` — a REassignment — so a const declaration with a call value, which is how a handover is almost always written in TS/JS, produced no capture and the binder had nothing to bind. Both fixed; enforced by `tests/integration/features/pulse-handover.test.ts`, whose fixture uses the const form deliberately because a reassignment fixture passes with the second cause still present. Confirmed red against a build with the collector removed
- [x] `PULSES_TO` joined the `EdgeType` union. It was written as a cast, which is how an edge type stays invisible to every exhaustive switch over that union — part of why nothing noticed the vault held none
- [-] CARRIED to todo25#P7 and closed there. FOUND BY THE FIX, and it is a design question rather than a bug to patch quietly: a persisted `PULSES_TO` edge has a DANGLING SOURCE. `producer.targetId` is the variable name (`value`), which is not a node id, so the edge points from something the graph does not contain. `audit` does not flag it because its orphan check reads targets only. Decide what the source of a handover edge should be — the producing call's target, the scope, or a materialised local — and say why in an ADR before changing it. ## Phase 2 — the remaining twelve guessers each refuse or label
- Depends: todo24#P1
- Builds: 0046
- [x] Every CALLS edge carried 0.85 whether its target resolved or fell through to a bare name, and every heritage edge carried 1.0 whether the clause was captured or guessed from an `I` prefix. Unresolved is now 0.4 and inferred heritage 0.6, so `WHERE confidence < 0.6` can finally separate them; 3 of the 5 cases in `guess-confidence.test.ts` were confirmed RED against the flat values
- [x] FIRST, because 0046 introduced it: a rebind IS a resolution, so `rebindEdgeTarget` now lifts an edge out of the guessed band (below 0.6) when its target becomes known, and `updateEdgeTargets` writes the same rule to the vault with a CASE so only guessed rows move. Two tests in `guess-confidence.test.ts` cover both directions — an edge at 0.4 becomes 0.85, and one at 0.6 (inferred heritage, a judgement rather than a give-up) is left alone
- [x] `getCommitsBehind` returns `null` on failure instead of `0`, and NaN from an unreadable answer is null too rather than falling through `|| 0`. The staleness banner now prints "an unknown number of commits (git could not be read)" instead of "0 commits behind" — the one case a user most needs telling was the case that produced the reassuring line
- [x] `readSingleFile` returns null when a file cannot be read, and `streamBatches` DROPS those rather than handing them on as empty source, naming each one in a warning. An unreadable file used to be hashed, recorded in the gate and given a unit node with no symbols — so a permissions error looked exactly like a blank file, and the hash gate then skipped it on every later run. `readFile`, the single-file reader whose callers want content or nothing, still coalesces to '' on purpose
- [x] `getCommitResonance` carries `unavailable: true` when git could not be read, separating it from a symbol that genuinely has no commits. Both used to return a bare `{0,0}`. NOT YET DONE and deliberately separate: entropy still treats the two the same because it reads only the counts — the data now distinguishes them, the consumer does not. Carried below
- [x] MEASURED first: 15 basenames in this repo are duplicated, `index.ts` occurring 24 times, `queries.ts` 13, `resolver.ts` 11 — so resolving an unresolved `index` import by first-in-order was right about one time in twenty-four, and wrote an edge indistinguishable from a correct one. The fallback now answers only when the match is UNIQUE, on both the exact-basename and the prefix path. Refusing costs an edge; guessing costs a wrong edge, and a wrong edge is what `impact` and `trace` walk. Four tests in `import-ambiguity.test.ts`, two confirmed red against first-match
- [-] MEASURED, and left alone: the `.h` sniff was run over every header available locally, including the labelled corpus in `archive/polyglot-test-lab` — 3 known-C++ headers and 6 known-C ones. It classified 9 of 9 correctly. The sample is small and says nothing about templates-only headers or C++ that avoids the four tokens, but a heuristic with a measured 0% error on the only labelled data present should not be swapped for another guess. Dropped rather than deferred: it will be reopened by a real misclassification, not by a schedule
- [-] MOVED to todo25#P8, which is live — closing this file would have buried it. MEASURED at 11%, and deferred with a reason. Of 602 CONSTRUCTS edges in this vault, 144 resolve to a node: 128 land on a `struct` (correct — TS classes are captured as struct) and 16 land on a `variable` or `property`, which are not types. The 458 dangling ones are mostly correct constructions with unresolved module paths, so dangling was indeed not the same as miscategorised. Deferred because the fix is not a better regex: the CALLS-vs-CONSTRUCTS decision is made by the caller before `CallProcessor` sees it, so the confidence channel ADR 0046 opened cannot carry it, and separating a capitalised constant from a class needs type information the parse does not have. Reopen when the reflector can pass its own certainty down
- [x] `discoverRoot` still falls back to `cwd` — refusing would break a scratch directory, a fresh checkout before its manifest exists, and every test fixture — but it now WARNS with the directory it chose and the full list of markers it failed to find. Silence was the actual defect: the `/private/tmp` analyze looked normal the whole way through because nothing ever named the root it had picked
- [x] Entropy turned out to read `getAuthorDistribution`, not `getCommitResonance` — and it had the identical flaw, returning `{}` for both "no authors" and "git failed", which produce the same entropy 0 and risk 0. It now returns null on failure and both `calculateEntropy` implementations report `unavailable` instead of a confident zero. Three tests in `chronicle-interface.test.ts` cover the three git-failure paths and were confirmed red against the old returns
