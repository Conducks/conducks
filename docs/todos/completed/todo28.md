## Phase 2 — a tool that cannot be called over MCP
- [x] `conducks_coverage` returned **213,106 characters / 680 functions** and the transport rejected it outright. It has no `limit` parameter, unlike `query`, `prune` and `flows`, and no token budget, unlike `context`. On any project larger than this one it is strictly unusable. Reproduced 2026-07-31 via a fresh stdio JSON-RPC call against build/ (`node build/src/interfaces/cli/index.js mcp`), matching the number in this task exactly
- [x] It reported `meta.truncated: false` on that response. The field is not merely unhelpful, it is false — the answer WAS cut off, by the transport rather than by the tool. Every other tool sets this honestly. Fixed: `meta.truncated` is now `shown.length < bound.length`
- [x] Fixed: added `limit` (default 75, max 500). Measured against the 680-function baseline by slicing the real 680-row response at N=30..100 through the tool's own `JSON.stringify(res, null, 2)` formatter — 75 -> 23,279 chars, 80 -> 24,832 chars (too close to the 25,000 ceiling), so 75 was chosen for margin. `summary` still counts the full 680/1/369 baseline; only `functions` is capped

## Phase 3 — trace does not return a trace
- [x] ROOT CAUSE was not what this line assumed. `trace()` at `kinetic/trace.ts:133` did `Array.from(bfs(...).keys())`, discarding the `{depth, path}` bfs already computes — but reordering does NOT fix it: dijkstra's min-heap already emits non-decreasing weight, verified by reverting an added sort and getting byte-identical output. Several direct calls TIE at equal graph distance and the graph carries no signal for which a reader would call first. Original: `conducks_trace --mode execution` on `AnalysisService.analyze` returned 10 "steps" including `global::promise`, `global::process` and `fs.stat`, with `synapsepersistence.beginpulse` LAST — it runs first. The result is an unordered neighbour set presented as execution order
- [x] Addressed by renaming rather than pretending: mode `execution` -> `reachability` (default), with `execution` kept as a working deprecated alias so no caller breaks, and the description rewritten to say plainly this is wiring, not execution order. Original: conducks-docs §6.13 makes exactly this distinction: `conducks trace` verifies wiring, never logic. The tool's own `mode: "execution"` claims the thing the standard says it cannot do
- [x] DECIDED: rename. Steps are also enriched from bare id strings to `{id, name, kind, file, line}`, so a caller can jump to one. The distance sort was kept as an honestly-labelled invariant guard, NOT counted as a fix, because it is a no-op against the current heap. Acceptance met via "no mode claims execution order". Original: Decide: order the steps by something defensible, or rename the mode to what it returns. Fixed when either the first step is the first thing that runs, or no mode claims execution order

## Phase 4 — half the graph is local variables, and the agent-facing tools return them
- [x] CAUSE FOUND AND THE ORCHESTRATOR'S FIRST DIAGNOSIS WAS WRONG. I read it as "`properties.rank` is undefined after a shallow load, so the `?? 4` fallback makes rankWeight a constant". It is not undefined — `rank` lives in the persisted metadata blob (0.1978 on `intralinker.resolve`, verified) and is restored on the full load every MCP process uses. The real mechanism: `rank` is a PageRank float clustering near zero, so `1/(rank+1)` sits in a narrow 0.67-0.97 band that barely separates kinds, and it rewards CENTRALITY rather than taxonomy depth, so a central local can outscore the function declaring it. Fixed by scoring on `canonicalRank` (STRUCTURE 7, BEHAVIOR 8, ATOM 11) — the field the comment already described. Original: MEASURED: **1,961 of 3,845 nodes (51%) are ATOM** — locals like `unitId`, `srcNode`, `abs`, `list`. `conducks_context` with a 1,500-token budget returned 19 nodes of which **10 were ATOMs (53%)**, so more than half the budget went to local variable names
- [x] FIXED — every returned symbol now carries `line` from `properties.range.start.line`, and honest `null` when the node genuinely has none rather than a fabricated number. MEASURED end to end over JSON-RPC: 0/19 -> 10/16. Original: **0 of those 19 nodes carried a line number.** Repo-wide, 152 of 1,224 BEHAVIOR/STRUCTURE nodes have none. An answer a caller cannot jump to costs a grep on top of the call that was supposed to replace it
- [x] ADDRESSED ADDITIVELY, not by replacement: every item gains a repo-relative `short_id` while the full `id` stays byte-identical, because `trace`/`impact`/`explain` were not taught to ACCEPT the short form and swapping it would break every caller that feeds an id back in. Teaching the other tools to accept it is left open and no todo carries it. Original: Node ids average **127 characters** (max 185) — roughly 32 tokens each before any information, and an id is the required input to `trace`, `impact`, `explain` and `context`, so a caller must first spend a `query` to obtain one
- [x] DECIDED: excluded by DEFAULT with an `include_atoms` opt-in, not merely down-weighted — a scoring tweak narrows the problem, exclusion bounds it. Original: These three compound: the tools that take an id and return neighbours are the ones where the noise, the missing line numbers and the id cost all land at once. Decide whether ATOMs are excluded from the agent-facing tools by default, whether ids can be repo-relative, and whether `file:line` is mandatory on every returned symbol
- [x] MET, verified over real JSON-RPC on the same symbol and budget: ATOM share 53% -> 0%, lines 0/19 -> 10/16
- [x] REVIEW CAUGHT A NEW INSTANCE OF THE BUG THIS TODO IS ABOUT. `include_atoms: true` was documented, admitted ATOMs to scoring (candidates 235 -> 273) and could never return one: a pre-existing 10% diminishing-returns cutoff dropped them all, so output was byte-identical with the flag on and off at a 20k budget AND at the 100k maximum. The agent's own fixture could not reproduce it — every fixture node sat at depth 1 with confidence 1.0, so scores clustered and the cutoff never fired. Fixed by skipping the cutoff when the caller explicitly opted in; a deep low-confidence ATOM was added to the fixture so the case is now reproducible, and the test was confirmed RED against the unfixed cutoff. `include_atoms:true` now returns 273/273 including 38 ATOMs
