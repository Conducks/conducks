## Phase 0 — measure before designing further
- Builds: 0035
- [x] MEASURED 2026-08-01, and the answer is that reading an unchecked-out ref is CHEAP. Repo at `7074b39`, 551 tracked files (the "~1800" in this task was wrong by 3x), 4.4 MB, best of 3, all three methods verified to return the SAME 551 entries and 4,537,341 chars so the comparison is fair. `git archive` **53 ms**, `git cat-file --batch` **117 ms**, `git show` per file **5,655 ms** — 107x slower, at 10.3 ms/file, which is pure process spawn. A plain `fs.readFileSync` of the working tree is 21 ms, so `archive` is 2.5x a normal read. The number that settles it: a full `analyze --force` is 5.2 s, so reading a ref costs **~1% of a pulse**. ADR 0035's worry is correct about `git show` and irrelevant for `archive`. `archive` returns a tar stream needing ~40 lines of parsing; `cat-file --batch` hands back `(path, content)` natively for 64 ms more — the choice is ergonomics, not cost
- [x] NOT ESTIMATED — BUILT. Both layers were exported with `git archive` (`cd9cea1` and `cd9cea1~5`), analyzed into separate vaults and compared row by row, so these are measurements rather than a model. One layer: **17.05 MB on disk, 11.20 MB logical** — 4,168 nodes (6.59 MB) + 14,033 edges (4.61 MB), and `metadata` alone is 56% of every node row. Two layers: **2.00x** without content-addressing, **1.21x** with it, **1.07x** once graph-global columns are moved out of the addressed row. Node rows identical 68.6% as-is, rising to **91.8%** when `gravity`/`risk`/`depth`/`isEntryPoint`/`canonicalRank` are excluded; edge rows identical **97.7%**. `gravity` alone causes the 68.6→91.8 gap — a graph-wide float that moves for symbols in files nobody touched. **CONTENT-ADDRESSING COLLAPSES IT, so Phase 3 keeps its shape**, with one design constraint falling out of the data: graph-global metrics must live OUTSIDE the content-addressed row or a third of the duplication remains for nothing. ADR 0035's own storage figure is stale by ~40x — it records "roughly 100 KB per node" against a measured 2,534 B/node here and 2,248 B/node on mentorseed

The whole design rested on "pulsing an unchecked-out ref is cheap enough". **That number is now known
and the answer is yes**: `git archive` reads a whole ref in 53 ms against a 5.2 s pulse, and two
content-addressed layers cost 1.07-1.21x one layer rather than 2.00x. Phase 3 is unblocked and keeps
the shape ADR 0035 gave it.

Measured 2026-08-01. The gate this paragraph set has been met.

## Phase 0b — the two-layer measurement, settled
- Builds: 0035
- [x] RESOLVED 2026-08-01 by a third A/B run here, and BOTH earlier measurements were wrong — for different reasons, each of which made content-addressing look worse or better than it is. Two real adjacent commits (HEAD, HEAD~5) exported with `git archive`, analyzed separately, then loaded into ONE vault two ways. **Content-addressing WINS: 1.94x against flat's 3.43x for two layers — 0.564x, i.e. 44% smaller.** 48.4% of slots dedupe (4,535 unique rows backing 8,781)
- [x] THE HARNESS FAULTS, recorded because both are easy to repeat. FIRST: each layer was analyzed at a DIFFERENT absolute directory, so every `id` embedded the layer root and nothing could match — 4.4% shared, an artefact with no meaning. Real layers are one repo at two commits and share every path. SECOND, and the one that produced the dispute: the addressed row INCLUDED the volatile columns, so the content hash changed whenever they did and dedup fired **3.5% instead of 48.4%**. Hashing volatile data into a content key tests a strawman, not content-addressing
- [x] THE DESIGN CONSTRAINT, now measured per column across 4,370 ids present in both layers, replacing Phase 0's coarser version. VOLATILE, and must live in the SLOT row: `metadata` 92.9%, `rootId` 92.6%, `layer_path` 88.9%, `gravity` 26.3%. IDENTICAL on every shared id: `fingerprint`, `canonicalKind`, `canonicalRank`, `semantic_kind`, `file`, `namespaceId`, `unitId`, `structureId`, `depth`, `isEntryPoint`, `visibility`, `dna`, `signature`, `kinetic`. Excluding just the four volatile columns, **97.2% of shared ids have byte-identical stable content** — higher than Phase 0's 91.8%, and that number is the whole case for the design
- [x] STAMPED — ADR 0081 amends 0035, stamped both ends. 0035's mandate is upheld and its figure superseded: two content-addressed layers cost 1.94x against a flat 3.43x, not the 1.07-1.21x it cites. The measured column split lives in `src/lib/core/persistence/content-key.ts` with a test that FAILS on an unclassified column rather than letting it default into the hash — writing that test immediately caught 7 columns nobody had classified
- [x] ADR 0081's first open item CLOSED — read cost measured on the ADDRESSED shape, which 0081 only had a flat-shape number for. Best of 3, warmed, 8,781 slots: scan one layer **23.7 ms flat against 25.0 ms addressed (+5.5%)**; 200 point lookups **169.3 ms against 193.2 ms (+14%)**. So content-addressing costs 5-14% more read time for 44% less space, and the per-lookup figure (~1 ms) is DuckDB round-trip overhead rather than the schema — the delta is what the shape costs. Acceptable, and now measured rather than assumed
- [x] ADR 0081's second open item CLOSED — the different-day case, simulated NARROWLY: only `tenureDays` was advanced by 7 days inside `kinetic`, which is exactly the transformation a later analysis date applies, and 3,886 of 4,371 rows changed. Every other column kept its real measured value. **Correct classification (kinetic OUT of the hash): dedup holds at 48.4%. Naive classification (kinetic IN, as the 0%-volatile measurement would have shipped): dedup collapses to 5.3%.** A 9x difference, and it confirms the reasoning that overrode the number was right — and quantifies what trusting a blind measurement would have cost

**Phase 3 is unblocked and keeps ADR 0035's shape.** Build content-addressed, split the four
volatile columns into the slot row, and do NOT put `metadata`, `rootId`, `layer_path` or `gravity`
into the content hash.

## Phase 1 — the branch guard, useful on its own
- Builds: 0035
- [x] DONE in the contract freeze before the fan-out. `pulses.branch` added via `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` so old vaults stay readable, written from `chronicle.getCurrentBranch()`, which uses `symbolic-ref --quiet --short HEAD` and returns NULL on a detached HEAD rather than inventing a name
- [x] BUILT — refuses with exit 1 and names both branches. Refusal, never a warning: a warning above a full answer gets read as noise while the answer below it, describing a branch not on disk, gets taken. The guard's MEANING lives in two free functions with no git and no vault (`branchMismatch`, `branchRefusalMessage`) so it is assertable directly, with the git and persistence dependencies passed structurally — which was forced by the architecture gate, since `cli` may not import `core` (ADR 0005)
- [x] BUILT, and it POLLS rather than watches, for a reason worth keeping: a file watcher cannot see a checkout at all. Git only rewrites files that DIFFER, so identical files fire no event and differing files look like ordinary edits. Watching `.git/HEAD` fails too — checkout REPLACES that file, dropping an inode-bound watch, and worktrees keep it elsewhere. So it polls `symbolic-ref`. It stops the auto-pulse and reports; it does not rebuild, because stopping is recoverable and a vault blended from two trees is not
- [x] BUILT, report-only per ADR 0031, and included in the `--stale` filter — which matters because a branch mismatch is exactly the case where every hash MATCHES, so without it `--stale` hides the one project answering from the wrong tree. Spawns git per project root rather than using the `chronicle` singleton, which anchors to one directory and would have reported the same branch for every row
- [x] Asserted, and mutation-checked: `branchMismatch` always returning null kills 2, and dropping the vault branch name from the message kills 2
- [x] Asserted. Treating a null checkout as a mismatch kills 3 across the no-git and monitor suites

Ships independently and is not thrown away by the layer work. Today switching branch gives
confidently wrong answers to every question with no warning.

## Phase 3 — commit-keyed layers
- Builds: 0035
- Depends: todo20#P0
- [x] BUILT, and the second clause is DELIBERATELY NOT DONE — stated rather than quietly skipped. `node_slots` is keyed `(layerId, id)` and `node_content` by `contentHash`, so a node does belong to a layer and two versions coexist. But `nodes.id` REMAINS a bare PRIMARY KEY, because `nodes` IS the uncommitted layer: ADR 0035's model already separates the ONE mutable layer from the many immutable ones, and the mutable one holds exactly one version by definition. That wording presumed a single table for everything; the goal behind it — two versions coexisting — is met. The reason not to migrate `nodes` is risk, and it is measured risk: it is the hot path every command depends on, its write path carries a DuckDB workaround (ADR 0064) that a view cannot host, and `insertBatched`'s update/insert split exists for a bug that only bites under real pulse churn. Trading a measured win for that is a bad deal. The layer tables use a plain insert instead, which never re-writes a key and so cannot hit that bug at all
- [x] BUILT AND PROVEN. `writeLayerNodes` hashes only `CONTENT_NODE_COLUMNS` (ADR 0081), inserts each distinct row once and points every slot at it. The acceptance is asserted directly: 200 nodes in layer one, a second layer differing in 10 of them, and stored content goes 200 -> 210 — **1.05x, not 2x**. A stronger case pins the property the design turns on: two layers whose STABLE content is identical but whose `gravity`, `metadata`, `layer_path` and `kinetic` ALL differ still share every row, because those four are volatile and excluded by construction. Mutation-checked both ways — hashing the volatile columns as well turns that test red, which is exactly the 3.5%-versus-48.4% mistake ADR 0081 was written about. `dropLayerNodes` sweeps content no surviving slot references, so collection reclaims the BYTES rather than just the slots; skipping that sweep also turns a test red
- [x] THE READ HALF IS BUILT — `chronicle.readRef(ref)` returns every tracked file of a commit WITHOUT touching the working tree, and `resolveRef(ref)` resolves a ref or returns null rather than guessing. Verified on this repo: `HEAD~5` reads 569 files in **123 ms** against `HEAD`'s 574, and a file changed between them genuinely differs. `cat-file --batch` chosen over the faster `git archive` (117 ms vs 53 ms measured) because it hands back `(path, content)` natively where `archive` returns a tar stream needing its own parser — 64 ms to avoid a second format, once per layer. ONE process for the whole ref: the per-file spawn is the entire 107x that made `git show` unusable. TWO TRAPS are pinned by tests rather than left to be rediscovered — the batch output is delimited by the DECLARED BYTE SIZE, so a parser scanning for the next header-looking line truncates any file whose content contains one (there is a fixture that does), and `encoding: 'buffer'` is valid for `spawnSync` but THROWS `Unknown encoding: buffer` from `execFileSync`, which is what made the first version return null for everything. Still open: writing those files into a layer, which waits on layer-scoped rows. Original: Build a layer for a ref WITHOUT checking it out, using the chronicle's existing git-blob path
- [x] THE MECHANISM IS BUILT: `resolveLayerRole()` turns a ROLE into a layer id and `readNodesForRole()` reads through it — `uncommitted` from `nodes`, every other role from layer storage, which is the model rather than a special case. ADR 0035's naming is honoured exactly: the roles are `uncommitted`/`current`/`target`, NOT `main`/`branch`/`uncommitted`, because that first draft privileges `main` and is the wrong baseline for anyone branching off `develop`. It REFUSES rather than falling back — an unresolvable `target` throws with a message naming what the user can do (set an upstream) and stating that conducks will not guess `main`, because a diff against the wrong baseline is the failure this project keeps shipping. Two mutations pin it: making `target` fall back to `current`/`main` kills 3 tests, and requiring git for `uncommitted` kills 2 — the second protects ADR 0035's promise that a project with NO git keeps answering. "Not built yet" returns empty and stays distinguishable from "could not resolve", since one means run a pulse and the other means git cannot answer
- [x] DONE, and NOT by rewiring thirty commands — the shape was wrong. Every read command obtains its graph through `persistence.load()`, so teaching THAT ONE METHOD about layers makes all of them layer-aware without any of them knowing layers exist: `load(graph, { layerId })` reads a commit layer from layer storage and the uncommitted layer from `nodes`/`edges` exactly as before. Thirty edits would have reached the same place while handing each command ROWS when what it needs is a GRAPH. This required building EDGE layers first (`edge_content`/`edge_slots`, same content/slot split as nodes, measured at 97.7% identical between adjacent commits) — without them a layer graph had nodes and no edges, which answers no impact or trace question and would have made the whole rewire hollow. Mutation-checked: making `load` ignore `layerId` turns 2 red, and dropping the edge-content sweep turns 1 red. The existing uncommitted path is untouched and pinned by its own case
- [x] THE RULE IS BUILT AND PINNED; the per-pulse CALL is not wired yet and waits on layers actually being written (the tasks above). `collectableLayers()` lives in `layer-reachability.ts` as pure functions over plain data, holding no database and no git, because that is where every dangerous mistake in this feature lives. THREE things are never collected and each is a way this could quietly destroy a working vault: `uncommitted` (it has no commit, so a naive "is your commit pointed at?" test collects the user's current work every single time), the ACTIVE layer (collecting what a reader is answering from empties the graph mid-session, and the emptiness reads as "this project has no symbols" rather than as a fault), and any layer whose commit is unknown (deleting on unknown is how data is lost). And an EMPTY pointer set collects NOTHING rather than everything — git returning no refs means git could not ANSWER, and treating silence as "nothing is reachable" would delete every commit layer at exactly the moment git is least trustworthy
- [x] COVERED at the unit level, on a REAL DuckDB vault: three layers recorded, one branch's commit dropped from the pointer set, exactly that layer collected and the other two surviving a list. Plus the three safety cases above and a case pinning that an old vault with no `active_layer` row still reads `uncommitted` rather than reporting nothing. MUTATION FOUND A VACUOUS GUARD and it was removed rather than papered over: a `kind !== 'uncommitted'` filter sat beside the id filter and NO test could be made to fail without it, because the id check and the null-commit check between them cover every case — belt-and-braces that cannot be shown to bite is a line the next reader has to reason about for nothing. Every remaining filter now goes red when removed. The end-to-end version (real branch, real pulse, real deletion) waits on layers being written by a pulse

- [x] BUILT — `mergeImpact(base, mine, theirs, callersOf)`, and the finding worth having is `changed-under-caller`: I change a function's shape, you change something that CALLS it, the two edits are in different files, git merges cleanly and says nothing. That is the collision only a structural graph can see, and it is why keeping one per ref pays. Two more kinds are classified: `both-changed` and `removed-under-caller`. Both sides are compared against the MERGE BASE rather than against each other — which is what makes it three-way, and is not decoration: A TEST CAUGHT A REAL BUG HERE, since two branches making the SAME edit merge cleanly and the first version reported every one of them as a conflict. It now compares the resulting fingerprints, not merely the fact of change. The caller lookup is a PARAMETER rather than a graph reference, so the classification does not change when callers start coming from a layer's own edges instead of the working tree's graph. Each symbol is reported once with its strongest classification, and uncomparable symbols are surfaced rather than counted clean — a merge report quietly calling unproven symbols safe is the ADR 0044 failure in the most expensive possible place. All three rules mutation-checked. NOT WIRED to a command yet: the edge half of a layer is not stored, so `callersOf` today can only be supplied from the working tree's graph, which is an approximation for a merge between two other refs
- [x] ASSERTED END TO END on a real vault: two layers written through content-addressed storage, read back, and diffed — one symbol edited, one deleted, one added, each landing in its own bucket, and `layersAgree()` false. The companion case pins the other direction, two layers holding identical code agreeing with zero incomparable. `diffLayers()` matches by ID FIRST so a symbol that stayed put is never a move candidate and a newcomer cannot steal its identity; only the unmatched remainder is offered to the fingerprint pass, and a fingerprint is trusted ONLY when unique on both sides — two symbols sharing a structure (an overload, a generated pair) would otherwise pair arbitrarily and report a move nobody made, so ambiguity falls back to add+remove. A move is ONE fact rather than an add plus an unrelated removal, which is what stops a rename reading as churn. All three rules mutation-checked
