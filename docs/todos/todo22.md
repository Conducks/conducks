# todo22 — the gates that do not run, and the claims that are not true
Status: todo
- Acceptance: every rule this repo declares is evaluated by something that runs automatically, and no doc claims an enforcement that does not happen.

## Context

Conducks exists to catch structural decay, and its own decay gates are either unrun or misdescribed.
None of this is new work discovered by building something — it is what an audit of the open board
found already true today, recorded because it was known and written nowhere.

The pattern is one this project keeps repeating and has a rule against (CONDUCKS-13): a check that
silently evaluates to nothing, and reports success. Seven shipped features have had that shape. These
are the same shape at the level of the gates themselves.

## Phase 5 — analyze ran out of memory, and the first diagnosis was wrong twice
- [x] `conducks analyze` died partway through with an out-of-memory error, leaving an empty vault and a non-zero exit. First recorded 2026-07-29 as "fails on 2 of 3 real projects benchmarked", which was WRONG on its own terms and is corrected in Phase 6: two of those three runs were not analyzing the project at all. The memory failure is real and is what this phase fixes; the subject it was attributed to was not
- [x] The cause is one statement per row inside the atomic pulse. `beginPulse()` (commit 34ba398) makes `saveNodes`/`saveEdges` stop self-committing, and DuckDB allocates transaction-local storage PER STATEMENT and coalesces none of it before the COMMIT. MEASURED on a 26-column table, 20,000 rows: 17,281 MB in one open transaction against 15 MB self-committing — 885 KB per row against 0.8 KB, a factor of 1150. The real run died at 19.1 GiB having written ~20k nodes, which matches
- [x] Two earlier explanations of this were guesses and both were wrong, which is the reason CONDUCKS-31 exists. "Pinned uncommitted rows exhaust the budget" named the wrong mechanism — the cost is per statement, not per row held. "It fails during the DISCOVERY flush, before wave 1" named the wrong place — it fails at wave 3. A third guess, that the duplicated `metadata` column was the weight, was measured at 1382 bytes average and 28 MB total and is irrelevant. None of the three was measured before being written down as fact
- [x] There was no tradeoff to decide. The recorded plan was to choose between per-wave commits, savepoints and a sibling-vault swap, all of which cost something. Because the cost is per STATEMENT, batching inside the SAME transaction fixes it and gives up nothing: 20,000 rows batched 500 at a time cost 169 MB against 17,281 MB, with the pulse still one transaction and still rolling back on a kill. `insertBatched()` in `persistence.ts` does this, and the batch is capped by PARAMETER count rather than rows — 26 columns x 2000 rows overflows the node driver's argument spread with `RangeError: Maximum call stack size exceeded` before DuckDB is reached
- [x] The error a user saw named the wrong cause. The OOM was logged once, then the aborted transaction made every later wave report `TransactionContext Error: Current transaction is aborted`, and THAT was what the CLI printed as fatal. A flush failure inside the pulse cannot be recovered from — the transaction is already aborted — so it now throws instead of being counted toward a circuit breaker. `flushAndClear` also only clears after a SUCCESSFUL write, so continuing kept re-flushing an ever-growing graph: waves 3, 4 and 5 of the failed run each reported ~6,600 nodes. The `pulseIncomplete` flag went with it, because nothing can set it once a failed flush rolls the pulse back, and a flag that cannot be set reads as a check that ran

## Phase 7 — a 470-file pulse peaks at 1.2 GB, and it is not the source or the graph
- [x] MEASURED 2026-07-29 on this repo, sampling the real node process rather than the subshell: a full `analyze --force` peaks at **1216 MB RSS and 204% CPU over ~46 s**; an unchanged pulse, where the hash gate skips parsing, peaks at **223 MB and 68% over under a second**. So roughly 1 GB belongs to the induction phase, and 223 MB is boot plus the graph load
- [x] Two obvious suspects were measured and are NOT the cause. Total source is **1.4 MB** across 287 files, so `allUnits` holding every file's text is a rounding error, not the weight. And the graph is 6,794 nodes / 17,663 edges, which an earlier measurement put at ~21 MB retained for 2,402 nodes — tens of MB, not hundreds
- [x] Wave size is not the lever either. Dropping `CHUNK_SIZE` from 500 to 100 moved the peak 1216 MB to 970 MB — 20% for five times the waves — and it CHANGED THE RESULT, 6,794 nodes against 6,823, because cross-file resolution sees a different set within each wave. Reverted rather than shipped: altering what the graph contains for a 20% memory win is the wrong trade, and the result-dependence is its own finding
- [x] It is NOT the JavaScript heap, which rules out every JS-side fix. The same pulse SUCCEEDS under `--max-old-space-size=400` and still peaks at 1043 MB RSS, so the memory is native. At the discovery flush the split reads rss=383 MB, heapUsed=101 MB, heapTotal=178 MB, external=50 MB, native=~150 MB, and native grows from there. `CONDUCKS_MEM_TRACE=1` prints this per wave
- [x] The twelve eagerly-loaded grammars are NOT the cost. Measured one at a time on this repo: 14 MB for all twelve together, largest single grammar 4 MB (csharp). Fifth explanation for this memory to be measured and killed
- [x] There is NO single cause, which is why five guesses missed it. MEASURED end to end with `CONDUCKS_MEM_TRACE=1` on this repo, 447 units, peak 1076 MB: modules 77 MB, +11 grammars, **+135 registry init**, +1 discoverFiles, +33 ignore filter, +5 vault reconcile, **+3 reading all 447 files**, +50 skeleton, +58 discovery flush, **+152 parse**, +7 reflect, **+177 vault write**, **+230 reloading the whole graph for PageRank**, +1 PageRank, +101 linkers and virtual induction
- [x] Native memory never comes back down. It climbs 49 MB to 742 MB across the pulse and no stage releases any of it, so the peak is the SUM of every stage rather than the largest one. That is the real shape of the problem and no single fix addresses it
- [ ] `persistence.load()` reloading the entire graph for PageRank costs **230 MB**, the largest single step, and it directly undoes the flush-and-clear the waves just did to save memory. PageRank is global by definition so it needs every edge — but it does not need them as JS objects. Cost a SQL or typed-array implementation before assuming the load is required
- [ ] Registry initialisation costs **135 MB** before a single file is read — persistence open, graph engine, ignore manager, chronicle git discovery. `external` alone goes 3 MB to 41 MB there, which is DuckDB buffers. Nothing has attributed this further
- [ ] Parse adds **152 MB** that is native and is never returned: after the wave, `heapUsed` falls back but `native` stays at 365 MB. Either tree-sitter trees are retained through the spectra, or the allocator is not returning them. This is the one place a native profiler is genuinely needed
- [ ] Revisit delete-then-insert for the vault write. It measured 22 MB against 212 MB for 20,000 rows written twice — a 10x win at identical wall time — and it avoids the MERGE path that crashes. It also broke the real pulse with `Duplicate key "id: ecosystem::path" violates primary key constraint`, which no standalone probe reproduced (overlapping ids, varying NULLs, file-backed and in-memory all survived). Find the mechanism before shipping it
- [ ] `CHUNK_SIZE` changing the node count is a correctness question wearing a performance costume. A pulse should produce the same graph whatever the wave size; if it does not, then either the wave boundary is leaking into resolution or one of the two counts is wrong. Reproduce by analyzing the same tree at 500 and at 100 and diffing the node ids, not the counts
- [ ] The benchmark harness must sample the real process, and it must live IN THE REPO. `scratchpad/bench/run.sh` watches `$!`, which is the subshell — every `peak_cpu` it ever printed was 0%. The replacement that descends to the node child and reports peak RSS and peak CPU exists only in a session scratchpad, which is deleted when the session ends, so every memory number in Phases 7, 11 and 12 was produced by a tool nobody else can run. Commit it under `tools/` before re-baselining

## Phase 8 — the batching fix shipped a nondeterministic crash, and the tests could not have caught it
- [x] `INSERT OR REPLACE` batched at 384 rows killed the process with `INTERNAL Error: Unaligned fetch in validity and main column data for update` inside `MergeIntoGlobalState::Sink -> PhysicalUpdate::Sink`. MEASURED at roughly one run in three, on a FRESH vault as well as an aged one, so neither vault corruption nor a timing artefact. It shipped in the batching commit and the whole suite stayed green
- [x] DuckDB processes in vectors of 2,048 rows and a batch that does not divide one straddles it, so the multi-row update path reads the validity mask and the column data out of step. `batchSizeFor()` now rounds the batch down to a power of two. Verified 20 consecutive clean analyzes across two projects, against a prior failure rate near one in three
- [x] A behavioural test could not have caught this and must not be trusted to: at one failure in three it passes two runs out of three while broken. `batchSizeFor()` is public so the RULE is asserted directly — every batch divides 2,048 and stays under the bound-parameter cap. This is the same shape as CONDUCKS-13, a check that can evaluate to nothing and report success
- [ ] Nothing else in the codebase is checked for this. Any other multi-row write — one added later, or one already present in a migration or a tool path — has the same trap and no test names it. Sweep for multi-row `VALUES` statements and confirm each is either single-row or aligned

## Phase 9 — three resolvers answered index questions by scanning the whole graph
- [x] `ImportResolver.resolveGlobal`, `SymbolLinker.fuzzyLink` and `getNeighborsByFilePath` each walked EVERY node to answer "which nodes have this name" or "which nodes are in this file", and each runs per import, per unresolved symbol or per file pair — so each was O(items x nodes). Two of them also COPIED the whole node map on every call. `clearFile` did the same, once per file being re-indexed, before any parsing happened
- [x] The graph already had a `nameIndex` and all four ignored it. Added a lowercase name index and a file-path index beside it, both maintained in `addNode`, `clearFile` and `clear`, and all four call sites now do a map lookup. Pinned by `tests/unit/core/graph/node-indexes.test.ts`, whose removal cases matter more than its lookup cases: an index kept on add but not on remove hands out ids for nodes that no longer exist and the resolver then binds an edge to nothing
- [x] An index keyed on a MUTABLE value needs the old entry dropped on overwrite. A node re-added under a changed name or path left its old entry standing, and because `clearFile` reads that index to decide what to purge, a pulse deleted nodes belonging to a different file — the node count shifted by 5 before this was found. `unindex()` is the one place that undoes what `addNode` recorded
- [x] `bindRouteCircuits` compared every request against every route and compiled a FRESH RegExp inside the comparison — O(requests x routes) regex compilations. Routes are now bucketed by method, each pattern is compiled once per route, and a route with no parameters is a string comparison instead of a regex. Compilations drop to O(routes)
- [x] Short-circuiting route binding on the first exact match was tried and REVERTED. The original bound a request to every route it matched, so stopping early silently dropped edges where two routes share a path — a behaviour change wearing a performance costume. Verified by output: with it, the vault differed from the baseline; without it, `analyze` produces an identical 6512 nodes / 17270 edges
- [x] `bindPulseCircuits` re-scanned a node's assignment edges once per call ARGUMENT, splitting every target id on every scan. The assignments are now indexed once per node and each id is split once
- [ ] These are correctness-preserving and their WIN IS UNMEASURED on this project. conducks has almost no routes or requests, so route binding is trivial here, and the resolver scans are a small share of a pulse that is dominated by parse and vault write. The complexity is now right; whether it shows up needs a project with many HTTP routes or many unresolved cross-file symbols

## Phase 10 — the vault write path failed three different ways, and tests caught none of them
- [x] `INSERT OR REPLACE` batched multi-row compiles to a MERGE and DuckDB dies inside it — `INTERNAL Error: Unaligned fetch in validity and main column data for update`, 2 runs in 3 on this repo's source. Replaced with DELETE-then-INSERT, which never compiles a MERGE and costs 22 MB against 212 MB for 20,000 rows written twice
- [x] Rounding the batch to a power of two, to "align" with DuckDB's 2,048-row vector, was the FIRST fix and it was WRONG. Twenty-five consecutive clean runs looked like proof; a different input then crashed 4 times out of 4. It explained the error message, not the error. Recorded in ADR 0041 as a rejected option so the theory is not rediscovered
- [x] DELETE-then-INSERT then failed a THIRD way, on an aged vault only: an id written twice in one pulse (the skeleton, recorded by the discovery flush and again by a wave) cannot be deleted and re-inserted inside the same transaction — DuckDB keeps the key of the earlier insert. Instrumented to confirm the id appears exactly once in the batch and once in the call. A repeat write is now an `UPDATE`
- [ ] NONE of the three failures is caught by a test, and every one of them shipped green. `tests/unit/core/persistence/pulse-replay.test.ts` now replays a pulse in its real shape and DOES cover the invariants they broke — last-write-wins for an id written twice in a pulse, and rollback to exactly the previously published graph — but mutation-checking says plainly that it does not reproduce the failures themselves: removing the repeat-write fix leaves it green
- [x] Seven variables were added to that fixture while trying to reproduce the duplicate-key case, and each was ruled OUT as sufficient — a committed first pulse, the same id written twice in one pulse, `purgeUnits` before the flushes, `updateRanks` mixed into the same transaction, several batches' worth of rows, realistic row size (a real `metadata` averages 1382 bytes, which decides how many rows fit a DuckDB vector), and an aborted pulse in between. Recorded in the fixture's own header so the next attempt starts from evidence instead of repeating them
- [ ] What is still missing is either the parts the fixture omits entirely — `load`, `resonate`, the linkers, `pruneTaxonomy`, compaction — or sheer scale: the failing call carried 6,249 rows across 25 batches against the fixture's 1,801 across 8. Try scale first, it is the cheaper of the two
- [ ] Until then the vault write path is verified by running `analyze` against an aged vault and nothing else. That is a real gate, not a missing one, but it is manual — so it must be run before any release, and `todo16` should say so
- [ ] The honest shape of the gap: these are all DuckDB behaviours under an open transaction, and the tests use short transactions with few statements. A fixture that replays a recorded pulse's statement sequence against a seeded vault would cover all three at once. Cost it before writing more one-off cases

## Phase 12 — the mid-pulse reload compressed data nothing ever read
- [x] `persistence.load()` used `SELECT *` and the driver materialises all 26 columns as JavaScript values — MEASURED at 190 MB to fetch 6,544 node rows, about 29 KB per row for data that is a fraction of that. It now selects only the 15 columns the method reads. `dna`, `signature` and `kinetic` are deliberately not among them: they are stored BOTH as their own columns and inside `metadata`, so selecting them cost three extra JSON parses per node for values immediately overwritten with equal ones. Fetch drops to 156 MB
- [x] The larger half was compression nobody asked for. `addNode` zlib-deflates every node's non-skeleton properties, and `getAllNodes()` — which is what the ranker, the linkers and virtual induction all use — returns skeletons and NEVER the compressed half. MEASURED at 102 MB to ingest, plus 110 MB of `external` Buffers. The analyze reload now passes `shallow: true` and skips it: ingest drops from 102 MB to 1 MB and `external` from 110 MB to 3 MB
- [x] Verified behaviour-preserving by A/B on identical source: shallow and full both produce 6518 nodes / 17297 edges, 1438 cross-file resolutions, 2700 virtual symbols and a vault of 2210/12909. Every other caller of `load()` — the mirror's `hydrateNode`, `diff`, `explain`, `entry`, `rename` — still gets the full load, so nothing that needs the meat lost it
- [x] Peak RSS **1053 MB to 871 MB, down 17%**. Together with deferring the boot load in Phase 11 the pulse went 1073 MB to 871 MB, down 19%, with wall time unchanged
- [ ] `getNode()` inflates zlib and re-parses JSON on EVERY call when meat is present, and the resolvers call it per candidate. That is invisible on the analyze path now that the reload is shallow, but `explain`, `rename` and `diff` still load with meat and then call `getNode` in loops. Measure whether those paths want shallow too
- [ ] `bindRouteCircuits` reads `node.properties.isRoute`, and `isRoute`/`isRequest`/`url`/`method`/`path` are NOT in the skeleton `addNode` keeps. So after ANY reload it sees undefined and binds nothing — it can only ever have worked in the same process that parsed the routes. Found while checking whether shallow loading would break it; it was already broken. Either promote those fields into the skeleton or state that cross-service binding is parse-time only
