## Context

Conducks exists to catch structural decay, and its own decay gates are either unrun or misdescribed.
None of this is new work discovered by building something — it is what an audit of the open board
found already true today, recorded because it was known and written nowhere.

The pattern is one this project keeps repeating and has a rule against (CONDUCKS-13): a check that
silently evaluates to nothing, and reports success. Seven shipped features have had that shape. These
are the same shape at the level of the gates themselves.

## Phase 5 — analyze ran out of memory, and the first diagnosis was wrong twice
- [x] `conducks analyze` died partway through with an out-of-memory error, leaving an empty vault and a non-zero exit. First recorded 2026-07-29 as "fails on 2 of 3 real projects benchmarked", which was WRONG on its own terms and is corrected in Phase 6: two of those three runs were not analyzing the project at all. The memory failure is real and is what this phase fixes; the subject it was attributed to was not
- [x] The cause is one statement per row inside the atomic pulse. `beginPulse()` (commit 34ba398) makes `saveNodes`/`saveEdges` stop self-committing, and DuckDB allocates transaction-local storage PER STATEMENT and coalesces none of it before the COMMIT. MEASURED on a 26-column table, 20,000 rows: 17,281 MB in one open transaction against 15 MB self-committing — 885 KB per row against 0.8 KB, a factor of 1150. The real run died at 19.1 GiB having written ~20k nodes, which matches
- [x] Two earlier explanations of this were guesses and both were wrong, which is the reason CONDUCKS-31 exists. "Pinned uncommitted rows exhaust the budget" named the wrong mechanism — the cost is per statement, not per row held. "It fails during the DISCOVERY flush, before wave 1" named the wrong place — it fails at wave 3. A third guess, that the duplicated `metadata` column was the weight, was measured at 1382 bytes average and 28 MB total and is irrelevant. None of the three was measured before being written down as fact
- [x] There was no tradeoff to decide. The recorded plan was to choose between per-wave commits, savepoints and a sibling-vault swap, all of which cost something. Because the cost is per STATEMENT, batching inside the SAME transaction fixes it and gives up nothing: 20,000 rows batched 500 at a time cost 169 MB against 17,281 MB, with the pulse still one transaction and still rolling back on a kill. `insertBatched()` in `persistence.ts` does this, and the batch is capped by PARAMETER count rather than rows — 26 columns x 2000 rows overflows the node driver's argument spread with `RangeError: Maximum call stack size exceeded` before DuckDB is reached
- [x] The error a user saw named the wrong cause. The OOM was logged once, then the aborted transaction made every later wave report `TransactionContext Error: Current transaction is aborted`, and THAT was what the CLI printed as fatal. A flush failure inside the pulse cannot be recovered from — the transaction is already aborted — so it now throws instead of being counted toward a circuit breaker. `flushAndClear` also only clears after a SUCCESSFUL write, so continuing kept re-flushing an ever-growing graph: waves 3, 4 and 5 of the failed run each reported ~6,600 nodes. The `pulseIncomplete` flag went with it, because nothing can set it once a failed flush rolls the pulse back, and a flag that cannot be set reads as a check that ran
